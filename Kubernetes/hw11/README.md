# Задание 1. Выбор стратегии обновления приложения

## 1. Исходные условия

Имеется приложение со следующими характеристиками:

- приложение развернуто в виде нескольких реплик;
- ресурсы кластера ограничены и не могут быть увеличены;
- свободный запас ресурсов в наименее загруженный момент времени — **20%**;
- обновление является **мажорным**;
- **новая версия приложения несовместима со старой** (отсутствует backward compatibility);
- требуется обеспечить контролируемое и предсказуемое обновление.

---

## 2. Анализ возможных стратегий обновления

### 2.1 Rolling Update

**Описание:**  
Поды обновляются поочерёдно: сначала поднимается новая версия, затем удаляется старая.

**Недостатки в данных условиях:**
- требует одновременной работы старой и новой версии;
- при несовместимости версий возможны ошибки протоколов, API и данных;
- увеличение количества подов во время обновления может превысить доступный
  запас ресурсов (20%).

**Вывод:** ❌ стратегия не подходит.

---

### 2.2 Blue-Green Deployment

**Описание:**  
Поддерживаются две полностью независимые версии приложения:
- Blue — текущая версия;
- Green — новая версия.

Трафик переключается после полной готовности Green.

**Недостатки в данных условиях:**
- требует удвоения ресурсов на время обновления;
- при доступном запасе только 20% невозможно развернуть вторую полноценную среду.

**Вывод:** ❌ стратегия не подходит.

---

### 2.3 Canary Deployment

**Описание:**  
Новая версия выкатывается на небольшую часть реплик,
на которые направляется часть трафика.

**Недостатки в данных условиях:**
- предполагает одновременную работу старой и новой версии;
- несовместимость версий может приводить к ошибкам при взаимодействии;
- усложняет маршрутизацию и контроль.

**Вывод:** ❌ стратегия не подходит.

---

### 2.4 Recreate Deployment

**Описание:**  
Все поды старой версии **полностью останавливаются**,  
после чего разворачивается новая версия приложения.

**Преимущества в данных условиях:**
- не требует дополнительных ресурсов;
- исключает одновременную работу несовместимых версий;
- полностью укладывается в имеющиеся ресурсные ограничения;
- логика обновления проста и предсказуема.

**Недостатки:**
- кратковременный простой приложения на время обновления.

---

## 3. Выбранная стратегия обновления

### **Recreate Deployment**

**Причины выбора:**
- ресурсы кластера строго ограничены;
- запас в 20% недостаточен для параллельного запуска новой версии;
- мажорное обновление без совместимости со старой версией;
- важнее корректность и целостность работы, чем отсутствие даунтайма.

---

## 4. Компромиссы и последствия

| Параметр | Оценка |
|---------|--------|
| Даунтайм | Кратковременный |
| Риск ошибок | Минимальный |
| Потребление ресурсов | Не увеличивается |
| Сложность реализации | Низкая |
| Контроль обновления | Высокий |

---

## 5. Заключение

В условиях жёстких ресурсных ограничений и отсутствия совместимости между версиями,
**стратегия Recreate является единственно корректным и безопасным вариантом обновления**.

Она обеспечивает:
- предсказуемость процесса;
- отсутствие конфликтов между версиями;
- соблюдение ресурсных ограничений кластера.

Данный подход особенно оправдан для мажорных обновлений,
где допустим кратковременный простой сервиса.
